Notable observation on step 9 session-picker: after step 7 (non-elev EXE run) AND step 8 (lnk-root elev EXE run), sliver-server had THREE sessions in play (`95ec803b` shellcode + `a5f01db2` from step-7 non-elev EXE + `7d5cfa56` from step-8 elev EXE). Step 3 (simulate-execute-shellcode-windows) surfaced a PowerShell type-conversion bug in the ART action YAML: `[W]::WaitForSingleObject($h, 0xFFFFFFFF)` throws `Cannot convert value "-1" to type "System.UInt32"` because PowerShell parses `0xFFFFFFFF` as System.Int32 (overflows to -1). Sliver session STILL landed because `CreateThread(0,0,$p,0,0,0)` on the preceding statement fired the shellcode in a background thread; the failing WaitForSingleObject only meant PS returned to the prompt instead of blocking. Fix (post-2.0, in `data/actions/simulation_user_interaction-v2/simulate-execute-shellcode-windows.yml`): replace `0xFFFFFFFF` with `[uint32]::MaxValue`. Runtime consequence: if the operator closes the PS window prematurely the shellcode thread + sliver session die with it — kept the window open throughout this pilot as a workaround.

Step 11 (`art-t1003_002-pypykatz-live-lsa`) failed with `AioRpcError: implant timeout` at 34.1s — identical failure mode to `20260715T033724Z/chain-003` pick #1, documented in that chain's ISSUES.txt (sliver implant task deadline enforced server-side; not solvable from sliverpy client). Real-attacker fidelity: a cold-start operator dropping pypykatz on Server 2022 would hit the same wall. Deliberately unpatched.

Step 13 (`art-t1486-gpg4win-encrypt`) failed with `CommandNotFoundException` on `C:\Program Files (x86)\GnuPG\bin\gpg.exe` — GnuPG is NOT pre-installed on Server 2022 default images. Mitigation option if a "gpg-encrypt-succeeds" chain is later needed: split action into "provision gpg4win" (idempotent) + "gpg4win-encrypt" (fast, once installed), OR replace T1486 impact with a native-Windows alternative that doesn't require a third-party binary (e.g., `Compress-Archive` + `Cipher.exe` combo — different technique, same tactic).
